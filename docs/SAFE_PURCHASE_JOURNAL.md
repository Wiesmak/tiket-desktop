# Phase 4 purchase journal and recovery

## Current Phase 5 continuity and administration journal

PurchaseJournal/v1 schema and exact replay bindings are unchanged. Native purchase/reprint remain enabled under verified grants, quote/review, journal durability and backend business preconditions. Historical Phase 4 records reopened successfully. Event cancellation now also suppresses old-context purchase callbacks without losing original durable outcome recording.

AdministrationJournal/v1 is separate: administration.v1.dpapi, its own writer lock and encrypted durable snapshots. Records retain exact method/protobuf/key and profile/backend/issuer/client/subject/event. PREPARED and SENDING commit before dispatch. Lost replies/crash reopen UNKNOWN. Explicit recovery reuses original bytes/key/subject; exact response bytes commit before success.

The optional Rejected marker records only a definitive rejection of the first transmission. An UNKNOWN replay rejection cannot disprove an earlier commit and remains UNKNOWN. A changed action/version requires fresh human review. Corruption, missing snapshot, unsupported schema, pending replacement, quota and persistence failure fail closed.

LocalPlans/v1 is a separate encrypted, context-bound draft store. A frozen request/key cannot be overwritten/discarded as an editable plan. Server ACK/read-back does not make DRAFT editable. VALIDATION_PHASE_5.md records the real committed/suppressed-ACK/fresh-native-recovery proof and one-effect SQL verification. Fault injection is ignored lab tooling, never a shipping flag or automatic retry.

Historical notes below are preserved. The current Phase 5 section above governs conflicting status.

`MutationJournal` and `JournaledMutation` support the native purchase/recovery/reprint controls through ConnectionSession. Controls require a verified access-token operating context, a reviewed server quote and protected local storage. Development acceptance remains incomplete; see VALIDATION_PHASE_4.md. Enabled software controls are not permission to test production funds.

ConnectionSession uses `%LOCALAPPDATA%/Tiket Desktop/PurchaseJournal/v1` (subject to normal packaged-app path virtualization). It requires a local fixed drive and Windows ownership, creates a protected current-user ACL for a new directory, and rejects existing Allow entries for identities other than the current user, SYSTEM and Administrators. DPAPI protects the snapshot contents. Tests use unique temporary directories and never read ProgramData, Docker, credentials or the managed connection profile. Concurrent app instances fail closed on the directory writer lock.

Schema 1 stores a complete JSON snapshot protected with Windows DPAPI CurrentUser through crypt32. All request/response bytes, subject, endpoint, issuer, client, profile, event, POS, player, cashier, coupon/key, reviewed quote and timestamps are inside the protected blob. No plaintext database, WAL, backup, export or temporary snapshot is created. Temporary `.pending` files are encrypted. In-memory buffers cannot promise forensic zeroization of managed strings/serialized objects.

An exclusive `FileShare.None` handle to `writer.lock` is held until disposal. A second instance cannot open that directory. Within an instance, a monitor serializes state changes. Snapshots use CreateNew, WriteThrough, Flush(true), then same-directory Windows MoveFileEx(REPLACE_EXISTING | WRITE_THROUGH); committed ciphertext is reread before dispatch may continue. This depends on Windows and the storage device honoring flushes. Power-loss and device-specific durability acceptance remains outstanding.

PREPARED records are immutable. SENDING must commit before invoking the supplied transport. Reopen converts SENDING to UNKNOWN and commits that classification. Recovery must be explicit: retransmitting UNKNOWN can complete an earlier uncommitted purchase. It preserves request bytes, coupon and idempotency key. No retry loop, automatic re-quote, offline sale or replacement key is implemented. Every post-dispatch exception remains UNKNOWN conservatively; proven rejection classification is pending. Received acknowledgements are validated against the reviewed pricing and identifiers and saved even if cancellation arrives after receipt.

Persistence failures quarantine the instance. An interrupted `.pending` commit blocks reopen pending investigation; it is never automatically discarded. A missing snapshot with an existing lock marker also blocks initialization. Do not delete the marker or pending snapshot to make the app start. Inspect both encrypted candidates with the original Windows identity and retain their originals before any approved repair. No repair utility exists yet.

Display/replay lookups require exact profile/backend/issuer/client/subject/event/POS equality. Reprints must link an ACKED original under that binding; their request/key is separate. Native login independently validates the access token's RS256 signature, issuer, API audience, lifetime and subject equality with the validated ID-token subject, then reads exact CASHIER/event/player/POS/cashier claims. A failed financial-context validation leaves read-only sign-in available but purchasing unavailable. POS choices come from verified token claims; no lab IDs or cashier values are hardcoded in shipping business logic. The backend remains the authorization authority and enforces current grants on every call.

DPAPI CurrentUser isolates Windows accounts, not OIDC operators sharing an account. Subject checks prevent access through this API, but another process running as the same Windows user can decrypt the file. Separate Windows accounts or an approved isolated-key design are required before a shared-workstation pilot.

Unknown schemas, corruption/decryption failures, quota failures and incomplete commits fail closed. There is no automatic schema migration, deletion or retention timer. The snapshot is bounded to 10,000 records and 8 MiB plaintext / 16 MiB ciphertext; reaching limits disables further writes. UNKNOWN must never be automatically purged. An approved archive/retention and migration procedure is still required before enabling production use.

No backup is created automatically. A future backup must preserve the whole encrypted directory consistently while its writer is closed, together with the Windows DPAPI recovery capability. An older backup can omit may-have-been-sent intents and must not be treated as an empty history. Uninstall, deleting app data, Windows profile replacement and loss of DPAPI keys can make reconciliation impossible. Do not reset the lab/database epoch while unresolved records exist; a fixed endpoint and fixture UUID do not prove authority continuity.

The review dialog includes exact profile/backend/issuer/client, player, POS, cashier, server canonical selection/total and versions. Cancel sends nothing. Confirm rechecks the same session generation and unchanged quote before PREPARED. A pre-send failure retains a never-sent PREPARED record. Any ambiguity after SENDING remains UNKNOWN conservatively, including failed replay after a prior uncertain send. Status messages never infer no debit from GetCoupon absence or arbitrary gRPC errors. The existing server acknowledgement is saved even if sign-out happens after a reply; generation checks suppress another operator's panel updates.

Native history is limited to local journal records and the exact current binding. The app never claims POS-wide history. Manual print refresh resolves only known ACKED job IDs; historical purchase print status differs from current outbox state. DISPATCHED means adapter acceptance, never paper delivery. REPRINT is a separate explicitly confirmed journaled mutation; no automatic reprint runs after an error. Backend retries can duplicate output, and the serial receipt has no visible REPRINT marker. The authorized lab uses console output only.
